# runtime-e2e

Isolated runtime acceptance harness. It runs already-built, sha256-pinned artifacts in a private Docker network, drives them with Java probes, injects faults, and judges the resulting money and order state with oracles. It never builds or changes engine jars.

The single-host fixture proves process behaviour only. It cannot establish host-failure tolerance.

## Topologies

The manifest's `schema_version` selects the topology. `core-*` scenarios need a version 2 manifest and only they accept one.

- Core topology (`schema_version: 2`, `topology: core`, validated by `core_contracts.py`): the v1 layout. Roles are exactly `me0-2` (matching engine), `ae0-2` (order and ledger core), `fwd0`, `fwd1` (C++ ME forwarders), `bridge0`, `bridge1` (C++ settlement bridges), `projector`, `shadow0` (the shadow replica on the replica kinds, reserved on every other manifest) and `probe`. The v0.5 roles `oms`, `market`, `bridge` and `xprojector` are refused. PostgreSQL carries only the money-journal history projection.
- v0.5 topology (`schema_version: 1`, validated by `contracts.py`): three matching nodes, three assets nodes, OMS, settlement bridge, market gateway, money-journal projector and fresh PostgreSQL databases with TimescaleDB.

## Requirements

Python 3, Docker, PostgreSQL 16 binaries (`initdb`, `pg_ctl`, `psql`; TimescaleDB for the v0.5 topology), a Linux image addressed by `sha256` digest containing Java 21 and Python 3, and the pinned artifacts. Core slots run C++ binaries from `cluster-tools` (forwarder, bridge, `aeronmd` and its libraries), bind-mounted and pinned by sha256 and source commit.

Run the tools with plain `python3`, not `python3 -I`: they import modules from their own directory.

## Commands

```bash
# unit tests, no Docker needed
python3 -m unittest discover -s runtime-e2e -p 'test_*.py'

# probes for the v0.5 topology (compiled against the supplied jars, never changes them)
python3 runtime-e2e/build_probes.py --me-jar /abs/match-cluster.jar --oms-jar /abs/oms.jar \
  --output /abs/new-probe-dir

# probes for the core topology (CoreProbe against the core jar, JournalProbe against the ME jar)
python3 runtime-e2e/build_core_probes.py --core-jar /abs/core-cluster.jar --me-jar /abs/match-cluster.jar \
  [--ct-dir /abs/cluster-tools] --output /abs/new-probe-dir

# one scenario
runtime-e2e/run.sh --manifest /abs/manifest.json --scenario core-smoke --output /abs/new-evidence-dir
```

Copy the program entries from the probe directory's `probe-manifest.json` into the fixture manifest.

`CoreProbe` verbs added for money schema v8 (v9 adds the core's genesisId to the order-events end frame and the config report, printed as `genesis_id` and `genesisId`): `order-events from= [until=] [max=]` (order-event replay; pages to the bound or the head, and on an overrun records the lost range and continues from the oldest event the ring still holds), `user-balances user=`, `config-report` and `core-limits version= ttl_ms= cap= ring=` (an ADMIN config write, answered by AdminAck).

`sbe_layout.py` reads the money schema from the cut's core jar and refuses a schema file of any other version; the genesis reader refuses a config frame of another wire version. The nightly plans name `money_schema_version`, both plan sets must name the same one, and a night refuses a cut whose core jar carries another version.

Helper tools (each prints its own usage):

- `mk_manifests.py <kind> <tag>`: builds a core manifest of a named kind; every manifest of one kind differs only in `run_id` and `state_root`.
- `release_cut.py check | audit | precheck | activation-record | genesis-ids | record-builds`: checks a release cut manifest and derived fixture manifests against the artifact rules (pinned sha256, clean source commit, no test builds in product kinds, matching schema identities), audits a live state root, and writes activation records. Cut manifests are `rc2-cut/2` (repo key `core`); `rc2-cut/1` (repo key `assets`) is still read as written.
- `oracle_samples.py <new dir>`: writes clean synthetic oracle samples.
- `nightly.py`: the nightly runner (see below).

## Scenarios

Unknown scenario names fail closed.

Core topology:

- `core-boot`: genesis, authentication refusals and a core authority refusal.
- `core-smoke`: funding at genesis, gate open, creates reach dispatch.
- `core-boots-N`: N fresh boots (1 to 20).
- `core-drill-<name>`: fault drills such as `lostack`, `coreleader`, `meleader`, `fwdrestart`, `partition`, `fwdpause`, `driverkill`, `lifecycle`, `lifecycle-faults`. `core-control-<name>` are non-vacuity controls and `core-red-<name>` run known-bad builds that must fail. The full list is the `DRILLS`, `CONTROLS` and `REDS` tables in `core_drills.py`.
- `core-drill-<name>` on the replica kinds: the shadow replica and peer-loss drills (see "Shadow replica" below).
- `core-xver-*`, `core-act-*`, `core-rollback-*`: cross-version, activation and rollback cases against v0.5.0-beta state (`xver.py`, `legacy_tag.py`; the case table is in the `xver.py` docstring).

v0.5 topology: `critical-path-smoke`, `harness-negative-controls`, `false-ready`, `false-ready-ae`, `pruner-exception`, `offline-purge-rejoin`, `baseline-fault-reproduction`, `readiness-me`, `readiness-ae`, `readiness-lag-election-idle`, `log-channel-me`, `log-channel-ae`, `journal-oms-restart`, `oms-recovery-admission`, `oms-durable-request-id`, `execution-projector-replay-crash`, `oms-hold-release-authority`, `benchmark-preflight`, `benchmark-normal`, `benchmark-n-minus-one`. Fault scenarios need the pinned `java/FixtureProbe.java` helper and benchmark scenarios the pinned `java/BenchmarkProbe.java`, recorded in the manifest's `test_helper` and `benchmark_helper`.

## Run rules

- Every run needs a new run id and a fresh state root at exactly `<manifest dir>/fixtures/<run id>`. The output directory must not exist. State and evidence are never reset or reused; keep a copy of each manifest.
- Images are addressed by `sha256`, never by tag. Repeats change only the run id and state path.
- Core manifests require `timeouts: production`. Environment names are allowlisted per process (`PROCESS_ENV`) and per image (`IMAGE_ENV`); no value may carry a `-D...timeout` style override. The only exempt names are `FWD_DRIVER_TIMEOUT_MS=5000` and `BRIDGE_DRIVER_TIMEOUT_MS=5000`. Every engine member gets its own disjoint cpuset; the network is `--internal`.
- Credentials are minted per run (`credentials.py`): the core gets `CORE_AUTH_KEYS`, each client `CORE_AUTH_CREDENTIAL`. Secrets are redacted from every retained command line, output, log and probe state file before teardown.
- Teardown removes only Docker objects carrying both the run label and the run's ownership token, and only the owned PostgreSQL process. After an uncatchable signal, finish cleanup with `Fixture(manifest, attach=True).close()` (or `CoreFixture`). Never prune Docker or reset a database by hand.
- Keep manifests and state roots in a run directory outside every repository: `state_root` lives under the manifest directory and holds staged binaries.

## Results and oracles

Results are `PASS`, `FAIL` or `INCONCLUSIVE`; only `PASS` exits zero. All subprocess exits and outputs are retained, and the runner copies the harness sources into the evidence directory with their hashes.

- v0.5 money oracle: integer units (1e-8), fixed-price LIMIT orders, no fees or amendments, two equal observations after input closes. Missing genesis, pending state or an unmodelled movement is INCONCLUSIVE.
- Core oracles: `core_oracle.py` (money rules M1 to M14) and `order_oracle.py` (order rules O1 to O12) judge one `core-sample-v2` document (format in `oracle_model.py`), FAIL over INCONCLUSIVE over PASS.
- The journal is decoded in Python from the pinned schema XML in `schemas/` (`journal_decode.py`, profiles and hashes in `schemas/journal-profiles.json`). Unknown records stop the decode.
- Smoke request timings include orchestration and are not performance measurements. A benchmark baseline needs all declared repeats; one repeat is not enough.

Known limits:

- The order tap loses order events across a core leader change. After the tap ends, the drill replays each order-event gap from the core (`CoreProbe order-events`, the any-user ADMIN key): a replayed event the tap also saw must match it byte for byte or the run fails, and a fully replayed gap closes the window. A gap older than the core's event ring stays open and is declared untappable with its `events_short` count; only that is INCONCLUSIVE (`tap_loss`), never FAIL.
- Restarting a core member shortly after a kill can hang the JVM on an active mark file. The drills wait before restarting.
- Inside a container the `aeronmd` pid is always the same, so driver identity is the `cnc.dat` mtime plus the container start time.

## Shadow replica

The replica kinds fill the `shadow0` role with the core jar as `CORE_ROLE=replica` (one artifact: `artifacts.shadow` must be byte-equal to `artifacts.ae`) and run the AE members in `SNAPSHOT_MODE=shadow`. The role names keep the `ae*` spelling of the fixture; the processes are the core.

- The replica launches through the engines' launch shape, never the C++ slot wrapper: `java -jar` embedded, the engines' staged `aeronmd` wrapper (`engine_libs`, `AERON_DIR=/dev/shm/aeron-shadow0`) external. Its driver mode is the engines' (`engine_driver`).
- Replica env (`core_fixture.replica_env`): `CLUSTER_REPLICA_SLOT=3`, `CLUSTER_REPLICA_ADDRESS`, `REPLICA_BACKUP_SOURCE=FOLLOWER`, `CORE_NODE_PORT` = the profile's `shadow_metrics` (19703), `SHADOW_PULL_SOURCES` = the three members' archive control endpoints spelled as `CLUSTER_ADDRESSES` spells them, `REPLICA_CATCHUP_RCV_WND=512k`, `REPLICA_SHADOW_BUFFER_MB=64`, `SHADOW_RETAIN_N=3`, the fixture's `TRANSPORT_LOG_TERM_LENGTH`, `ARCHIVE_SEGMENT_LENGTH=1m` and the replica's own `REPLICA` key (minted only for a manifest that runs the replica). Readiness is `/ready` on 19703.
- Member shadow block (`engine_env`, AE members only): `SNAPSHOT_MODE=shadow`, `SHADOW_PULL_SOURCES` = the replica then the two peers, `SHADOW_PRODUCER_BUFFER_MB=64`, `SNAPSHOT_INTERVAL_MINUTES=1`, `SHADOW_WITNESS_ALARM_MS=120000`, `ARCHIVE_SEGMENT_LENGTH=1m`. No `TRANSPORT_LOG_RCV_WINDOW`: the member derives its window from the term and logs it at boot.
- Archive segments: the replica and full kinds set the core's `ARCHIVE_SEGMENT_LENGTH=1m` on the members and the replica, so a 120 s story (about 22 MB of log) purges whole 1 MiB segments and the drills that need a log starting above 0 (peer loss loud and its companion, replica wipe, re-bootstrap) reach their precondition. Only the followers purge: the leader never pulls a shadow, holds no floor witness and keeps its log, so replica wipe and re-bootstrap wait on the followers' log starts (the replica's backup sources with `REPLICA_BACKUP_SOURCE=FOLLOWER`) and record the leader's. The core never read `fixture.JAVA`'s `-Daeron.archive.segment.file.length` (it sets the length explicitly; the flag stays for older artifacts); the older kinds keep the core's 64 MiB default they were measured on. `archive_listing` takes the segment length of the log recording from the member's `archive.catalog` descriptor, never from a constant.
- Kinds (all derived from the cut, `mk_manifests.py <kind> <tag> --cut <cut>`): `shadow` (slots external, engines and replica embedded), `shadow-ext` (engines and replica on the staged aeronmd), `shadow-anyverified` (members `SHADOW_ANCHOR_RULE=any-verified`) and `shadow-anyverified-ext`, `shadow-cooldown30` (`REPLICA_BACKUP_COOLDOWN_MS=30000`), `shadow-detectoronly` (`SHADOW_REBOOTSTRAP_REPLAY_FAILURES=0`, members any-verified), `shadow-query` (`REPLICA_BACKUP_QUERY_INTERVAL_MS=13000`) and `shadow-query-ext`, and `full` (no replica, `SNAPSHOT_MODE` unset, the same 1-minute cadence). The env a kind adds is the `REPLICA_KINDS` table in `core_contracts.py`; a control's setting lives in its kind because env lives in manifests.
- Drills (`replica_drills.py`): `core-drill-member-kill9`, `-peerloss`, `-peerloss-loud`, `-shadow-catalog`, `-supplierloss`, `-leaderloss-promotion`, `-replica-restart`, `-replica-wipe`, `-replica-rebootstrap`; controls `core-control-kill9-fullmode` (`full`), `-peerloss-loud-unblocked`, `-supplierloss-cooldown30`, `-rebootstrap-detectoronly`, `-rebootstrap-nowitness`. Every drill runs in both driver modes: on `shadow` and `shadow-ext`, except the shadow catalog and leader loss on `shadow-query` and `shadow-query-ext` (13 s backup query) and re-bootstrap on `shadow-anyverified` and `shadow-anyverified-ext` (the members must purge below the stopped replica); a control runs in one mode on its own kind. A control passes when both oracles pass, its named line fails with its text and the lines it keeps hold.
- Supplier loss passes when, within `SUPPLIER_LOSS_RECOVERY_BOUND_S` of the kill, `shadow_replica_backup_state` read RESET_BACKUP or BACKUP_QUERY (the backup left BACKING_UP), a new supplier is named and the applied position passed the leader's `core_log_position` at the kill. The bound defaults to 30 s: the recovery is the supplier's liveness timeout (about 3 s), the backup's 12 s cool-down, one backup query and the catch-up of what was written meanwhile, measured at 16 to 28 s (a 20 s bound failed one run in four). `shadow_replica_backup_resets_total` and `shadow_replica_reader_reattach_total` are recorded, not required: on Aeron 1.53.1 a supplier stop moves neither (the resets count possible-failure events only, and the backup extends the same local log recording).
- Leader loss, state (i) (the supplier won the election): re-validated within two backup query intervals (the backup state left BACKING_UP, or it already named another supplier), then a follower supplier and the applied position past the leader's log position at the kill within the query interval plus the cool-down. Whether `shadow_replica_supplier_is_leader` ever read 1 is recorded: with the FOLLOWER source the next response already names a follower. The lag of an attempt is held to the term unless the backup went through RESET_BACKUP in it.
- The shadow catalog bound is `CATALOG_ALIGNED_BOUND_S` plus the kind's `REPLICA_BACKUP_QUERY_INTERVAL_MS` (18 s on the query kinds, observed to `OBSERVE_FACTOR` x the bound): the replica learns of a member snapshot only at its next backup query and holds the ALIGNED until it has retrieved it.
- The detector-only control (`SHADOW_REBOOTSTRAP_REPLAY_FAILURES=0`) passes when the replica counted at least 3 replay-below-start refusals and was still running `MISSED_OBSERVE_S` later (re-bootstrap missed); the kit never reports this setting as "not taken" (its `/ready` reads 503 unverified continuation).
- Peer loss (and its loud variant) kill the replica and both followers, so the cluster loses its quorum and the tap's session closes until quorum returns. The core keeps no egress history, so what it emitted meanwhile cannot be tapped late. The drill declares that window untappable (`declared.untappable`: the tap's dispatch and order-event gaps that start at a `session_closed` inside the recorded quorum-loss interval and end at a `reconnected`): the barrier backfill still rebuilds what it can, a dispatch shortfall inside the window and an order whose terminal falls in it are recorded with the verdict (`untappable`, O-F5 `untappable`), not judged. An ME outcome without a dispatch is still judged. Leader loss (the promotion drill) records each election window, from the leader kill to the new leader serving, and declares a gap the same way when it starts at a `session_closed` inside one and ends at a `reconnected`; a session that survived the election (`new_leader`) declares nothing. The drill verdict carries `untappable` with the reason, the orders recorded unjudged and their count; the money oracle is unchanged. Peer loss loud keeps the leader as the survivor and blocks its archive port; its unblocked companion's survivor is the other follower, which holds pulled copies (a leader neither pulls nor produces, so it has nothing to serve), and the leader is killed instead.
- A dispatch gap that starts right after a `new_leader` note (the tap's session survived the election) closes when the core's superseded release mints account for every missed seq the backfill did not trace: a release mint that replaces a pending release takes the older seq out of the pending index, so the forwarders' resync never offers it. The arithmetic is `superseded = core_release_minted_up_to_total + core_release_minted_order_total - (tapped releases + ME-traced untapped releases)`, read from the AE member with the fullest count; the gap closes only when that number equals the untraced missed seqs and does not exceed `core_release_superseded_total` plus `core_release_abandoned_total` (an abandoned entry also leaves the index unseen). These counts are cumulative over the run: they show that enough seqs left the index unseen, not which ones; the equality is the real test. They are process-local (a restored member restarts them), so a run where every member restored from a snapshot keeps the gap open. It is recorded with the order oracle (`tap_superseded`) and the drill verdict (`superseded`). A core without `core_release_superseded_total` leaves the gap open as before.
- The peer-loss drills read the cut's cluster-kit from the pin its core jar carries (`replica_drills.kit_of`). On a kit at or below `0.1.23-runtime.20261118.rejoin.g8a6fb55` (by X.Y.Z, then on one X.Y.Z by the qualifier's runtime build date; two builds the date cannot order are INCONCLUSIVE) the rejoin watchdog trips during a genuine quorum loss: the members run `REPLICA_MEMBER_REJOIN_WAIT_MS` and the kit-default control `peerloss-loud-unblocked-kitwait` expects the survivor's watchdog exit. On a newer kit the watchdog is gated during a quorum loss: no override is applied and the control expects the survivor to outlast the quorum loss on the kit default (`survivor_outlasts_quorum_loss` holds). The witness records the kit (`kit`) and which wait applied (`rejoin_wait_override`). On a newer kit a survivor that still exits on the watchdog is the product defect `rejoin-watchdog-on-gated-kit`.
- Member kill -9 on the full kind: a member that restarts below the leader's log start and retries its election without exiting is the product defect `stranded-below-log-start`; before calling it silent the drill gives the member `LOUD_EXIT_BOUND_S` to exit. A kit with a catch-up watchdog exits such a member loudly (its `CRITICAL catch-up watchdog` line and the FATAL reason `member cannot catch up`, both naming its position, the leader's log start and the leader's member id). That exit is the expected loud failure (INCONCLUSIVE, the member is gone) only when the kit gave the member up: another member logged `member <id> STRANDED` (the leader held the floor past `RETENTION_MEMBER_WAIT_MS`, default 30 min, or `RETENTION_MEMBER_WAIT_BYTES`, default 2 GiB) or that its unknown floor passed the bound, or a member runs `RETENTION_FLOOR=report`. Otherwise the leader should have held its log and the member should have rejoined: the product defect `loud-strand-inside-retention-floor`. The harness's own arithmetic of the bound (lag behind the leader's snapshot, outage) is recorded in `loud_strand`; when it says the bound passed but no member logged the write-off, the drill is INCONCLUSIVE.
- Observation ends when the drill's last assertion is decided: after its fault steps, the story and the pre-barrier, the tap runs `TAP_SETTLE_S` (30 s) more and is stopped through its stop file (`CoreProbe tap stop=`, `core_fixture.stop_tap`). The tap's duration stays the summed worst-case bounds, so a step that waits to its bound only moves the stop later, and a tap that cannot stop early still ends there. `replica.json` records `tap_end` (decided, stopped, ended by `stop` or `duration`, seconds saved).
- Replica restart passes when the killed replica restores from its local shadow (LOCAL_SHADOW) and `/ready` answers 200 within `REPLICA_RESTART_READY_BOUND_S` of `docker start`. The bound defaults to 130 s: a LOCAL_SHADOW start reads 503 `unverified continuation` until its next ALIGNED compares byte-equal with the member snapshot the backup retrieved at that position, so the wait is up to one member snapshot cadence (1 minute on the drill kinds), one backup query (`REPLICA_BACKUP_QUERY_INTERVAL_MS`, 60 s by default) and the compare. The replica itself is back in about 2 s (applied at the leader's position); measured 3.1 s embedded, 14.8 s, 61.9 s and 62.1 s external (a 60 s bound failed the 61.9 s run); the 62.1 s run's log shows the LOCAL_SHADOW restore 1 s after start and the VERIFIED continuation at the first backup query 60 s after it.
- Re-bootstrap passes when the replica exits 3 and its own `CRITICAL replica restart (exit 3)` line states at least `SHADOW_REBOOTSTRAP_REPLAY_FAILURES` replay refusals. The scraped `shadow_replica_backup_replay_below_start_total` and `shadow_replica_rebootstrap_total` are recorded, not required: the process exits right after the refusal that decides, so the 0.5 s scrape can miss it (one run scraped 2 of the 3 the line states).
- Every bound and wait is a setting (`replica_drills.SETTINGS_SPEC`, overridden by an environment variable of the same name, range-checked) and is recorded with the run. A drill that cannot establish its precondition (a member snapshot, the pulls before a kill, a log that no longer starts at 0, a follower supplier) ends `INCONCLUSIVE` naming it. Every member a drill kills is restarted before the barrier, with `waited_after_kill_s` recorded; a replica restarted after a kill or an exit waits `SHADOW_RESTART_MIN_AFTER_KILL_S` (12.5 s) for its archive mark file, as an AE member does.
- Lag: `lag_sampler.py` runs once per drill inside the probe container (one process, never a process per sample) and writes `lag.tsv` and `summary.json`: `lag_bytes = core_log_position(leader) - shadow_replica_applied_position(replica)`, the leader's applied position (at most one duty cycle behind commit), with the replica's recorded-minus-applied alongside and the achieved sample rate. Time values here are functional guards of the fixture profile, never rate evidence.
- Faults go through the fixture's primitives only: `kill`, `pause`, `stop`, `restart` (`wait_ready=False` when the exit is the drill's to observe), `wipe_engine` (its replica branch needs no projection dump), `wipe_shadows` (an AE member's shadow recordings: the archive files its `recording.log` does not name) and the netfilter helper by port kind (`log_channel_fault.filter_arguments(..., port_kind='log'|'archive')`; an archive rule leaves loopback alone). The log start of a member is read from its archive listing on the host (`core_fixture.archive_listing`).

## Gateway and stream slots

A core manifest may declare four more roles: `gw0`, `gw1` (oe-gateway) and `st0`, `st1` (oe-stream). It declares all four or none. Each runs in its own container on its own GATEWAY key and its own cluster session, and reaches the core only over the network.

- Cuts are `rc2-cut/4`: `rc2-cut/3` added `repos.gateway` and the product artifacts `oe-gateway` and `oe-stream`; `rc2-cut/4` adds `oe-projector` and requires `substrate.aeron_patches` (each Aeron patch file of the cluster-tools lock: `lock_path`, `path`, `sha256`; `release_cut.py` re-hashes every file and refuses a set other than the lock's at `repos.cluster-tools`). Older cuts stay readable as written. Every gateway binary is built from the pinned gateway commit and pinned by sha256. A slot runs the cut's binary or a test-only alternative: `gateway_nc` (oe-gateway built with one `GW_NC_*` define; its build tree's `CMAKE_CXX_FLAGS` must equal the declared define), `gateway_stub` (`gateway_shim.py`, an HTTP shim over CoreProbe, never published) or `session_stub` (`ct_session_stub`, steered through `/data/stub.cmd`). The control builds are named by `MK_GATEWAY_NC`, `MK_GATEWAY_NC_NO_CANCEL_REOFFER_RULE`, `MK_GATEWAY_NC_NO_ASSET_CHECK` and `MK_GATEWAY_NC_NO_STALE_LABEL`.
- Users authenticate with per-run API keys, written to each slot's own `/data/api-keys` and redacted from every retained file. The gateway's users store is the PostgreSQL database `r01_gateway`. The treasury lane is on in every gateway kind: a TREASURY key per gateway in the members' `CORE_AUTH_KEYS`, plus `GATEWAY_ALLOW_TREASURY_LANE`, `GATEWAY_TREASURY_CREDENTIAL` and `GATEWAY_FAUCET_MAX_AMOUNT`.
- External driver mode: the slot's aeronmd runs as pid 1 of a sidecar container `<slot>-driver`, the way production runs it as its own service. The sidecar holds the slot's address and a shareable IPC namespace; oe-gateway or oe-stream joins those two namespaces only. A kill, a SIGSTOP or a restart of the binary leaves the driver running, and the restarted binary must attach to the same driver (otherwise the run is INCONCLUSIVE). The session stub keeps its in-container driver. A sidecar gets the slot's memory and CPU settings too, so an external slot's footprint is about twice an embedded one.
- Before the gateway slots start, the fixture moves the core to behaviour 4 (`core_behavior_step`); a kind's `behavior` can keep it at 3. Product slots answer on a fixed response port (`GATEWAY_RESPONSE_PORT`, 20480).
- All clients run in the probe container (`gateway_probe.py`): load with an Idempotency-Key per order, an order oracle per key, stream clients that record frames.

Scenarios (`gateway_scenarios.py`; each run writes `drill/drill.json`, a failing line carries its text, a missing witness makes the run INCONCLUSIVE):

- `gateway-kill-restart`: client load with keys on both gateways; SIGKILL of oe-gateway in `gw0` with requests in flight, restart; then the core leader is killed while unkeyed cancels are in flight (the old leader's egress to both gateways is dropped as it arrives, so a committed cancel is re-offered to the new leader), and `gw0` sends keyed creates once each in the same window (`REOFFER_CREATES_PER_USER`): a create committed before the kill is offered again by `gw0` under its own request id and must meet its stored decision, one order per key (`create_reoffer_once`); then the global gate is SUSPENDED while keys already answered are sent again, and the keys the closed gate refused are sent again after it reopens until each is decided (`GW_GATE_SETTLE_BOUND_S`). In external mode `driver_survives_gw0_kill` checks the driver.
- `stream-slow-consumer`: `st0`'s inbound core egress is thinned with the netfilter helper's `statistic` match on the response port (`SLOW_DROP_PERCENT`, default 99) while its driver keeps sending status messages and its process keeps its keepalives; the core's egress ceiling is lowered so the story reaches it in bounded time. Each stream user rests `SLOW_REST_PER_USER` orders first, so convergence is judged on non-empty sets, and `st0` must read not ready or open a new session epoch before the throttle is lifted.
- `gateway-session-timeout`: oe-gateway in `gw0` is stopped with SIGSTOP of its container's pid 1, sent by the daemon (`docker kill --signal=STOP`), and resumed with SIGCONT. In external mode its driver keeps running (`driver_runs_while_frozen`). `close_path` records which close branch fired.
- `fill-visibility-core`: n crossing pairs (default 200), closed loop, on one gateway and stream and across two of each. The pairs start only after every stream client holds a snapshot (the probe writes `pairs.ready` and waits for `pairs.go`). It records `fill-visibility.json` (accept, fill frame, order gone from GET /orders, polled from the 201 in its own thread, so the gone instant includes the gateway's read cache `GATEWAY_QUERY_MIN_INTERVAL_MS`) as data, never as a pass criterion. A REST fuzz runs before the money barrier; every request the core decided is in the money oracle.
- `tick-live-path`: a MARKET BUY with no budget and a stop complete on real ME ticks; a MARKET BUY on a market no tick ever priced answers 422 `NO_REFERENCE_PRICE`. With the forwarders stopped, a market that was priced keeps its last tick (the core holds no tick age): its MARKET BUY must be answered inside the bound, never hang, and the answer is recorded.

Kinds (`mk_manifests.py <kind> <tag> --cut <cut>`): drills `gw`, `gw-ext`, `gw-slow`, `gw-slow-ext`; controls, each passing only when its line fails with its text: `gw-freshkey(-ext)` (`second order for one Idempotency-Key`), `gw-b3` (`stored acceptance answered ADMISSION_CLOSED`), `gw-noreoffer` (`successful cancel answered NOT_FOUND`), `gw-noassetcheck` (`request unanswered: decode drop`), `gw-slow-ceiling16m` (`slow session not closed within bound`), `gw-timeout-shortfreeze` (a freeze shorter than the core's session timeout: `frozen session not closed within bound`), `gw-fill-muted` (`fill never visible`), `gw-tick-nofwd` (`market order not completed`). Dry runs: `gw-dry-stream(-ext)` and `gw-dry-stream-ceiling16m` (`st0 = session_stub`), `gw-dry-gateway(-ext)` and `gw-dry-gateway-freshkey` (`gw0 = gateway_stub`). Every size and bound is in `gateway_drills.SETTINGS`, and an environment variable of the same name overrides it.

Measurement (`gateway_measure.py`; data on the product binaries, never a pass line, in no night plan): `gateway-egress-cost` on a `gw` or `gw-ext` manifest records what the core sends to each client session and what each binary holds. Phases: idle (`MEASURE_IDLE_S`), a known load (`MEASURE_PAIRS` crossing pairs at `MEASURE_RATE` to `gw0`, users subscribed on `st0`) and, when `MARKET_SIM_BINARY` names a market-sim build, the simulator for `SIM_S` seconds against `gw0` and `st0` with its own API keys. Bytes are counted by target-less netfilter rules (inserted through the pinned helper) inside each slot's network namespace, on the slot's response port and per core member address; each phase also records the leader's, gateways' and streams' /metrics. Footprint: `/proc/1/status` and `du -sk /dev/shm` from inside each gateway, stream and driver sidecar container every `MEASURE_SAMPLE_S`, and `docker stats`. Output: `measure/egress-cost.json` and `measure/footprint-samples.json`. Settings in `gateway_measure.SETTINGS`, overridden by environment variables of the same name.

## Projection slots

A gateway manifest may also declare `pj0` and `pj1`, both or neither. pj0 writes the gateways' history database (`r01_gateway`); pj1 writes `r01_history_b`. A slot runs `history_projector` (oe-projector of the cut), in a control kind `history_projector_nc` (oe-projector of the cut's gateway commit configured with `-DOE_PROJECTOR_CONTROL=<PROJ_NC_...>`, the install tree holding oe-projector alone; its build tree's `OE_PROJECTOR_CONTROL` must equal its one declared define; the drop build also reads `PROJ_NC_DROP_SEQ`, default 2, which the fixture leaves at its default), or, in a dry-run kind, `projector_stub` (`projector_stub.py`, never published). The projector runs on the kind's driver mode (external: the staged aeronmd in the slot's own container) with its required `HISTORY_PROJECTOR_*` settings only: the listed core members' archives and node endpoints, the order journal (stream 4102, control stream 10, IPC MTU 1408, replay stream 4302), its GATEWAY key in `/data/cluster-key`, its database; everything else stays at the binary's defaults, except where a drill sets a setting and records it (the byte-equal drill's C: `HISTORY_PROJECTOR_BATCH_EVENTS`). In the follow drill the projection slots' staged aeronmd keeps a stopped client for `PJ_DRIVER_CLIENT_LIVENESS_S` (`AERON_CLIENT_LIVENESS_TIMEOUT` 60s, `AERON_PUBLICATION_UNBLOCK_TIMEOUT` 75s: the only values `core_contracts.PROJECTION_DRIVER_LIVENESS_EXEMPT` admits past the production timeout guard), recorded in the slot registry and the drill record. The core members then set `CORE_ARCHIVE_REPLAY_PROBE_STREAM` to that replay stream. The fixture creates the reader group `oe_history_reader` and the login role `runtime_history_reader` in it, and the gateways read history through that role. Its /health is read into the drills' keys (`core_fixture.projector_health_view`). The stand-in reads the core's order-event ring with `CoreProbe order-events fields=full` on its own GATEWAY key, holds a database lease, applies batches fenced by the lease, compares duplicates byte for byte, and beats only when a fresh head probe is at or below what it has applied. Its settings are `STUB_*` with defaults.

Kinds (`mk_manifests.py <kind> <tag> --cut <cut>`): `pj` and `pj-ext` (the drills on the projector binary, embedded and external), their controls `pj-nc-pinrecording` and `pj-nc-nostopreplay-ext` (`projector-me-restart-follow`; the no-stop build runs on the external driver, where a hung copy's subscription outlives the takeover), `pj-nc-wallclock` and `pj-nc-dropone` (`projection-byte-equal-replay`; the control build runs in every compared projection), `pj-nc-beatalways` and `pj-nc-nostale` (`history-freshness`; the latter runs gw0 as `gateway_nc` with `GW_NC_NO_STALE_LABEL`); the projector control builds are named by `MK_PROJECTOR_NC_<NAME>` (`PIN_RECORDING`, `NO_STOP_REPLAY`, `WALLCLOCK_COLUMN`, `DROP_ONE`, `BEAT_ALWAYS`). The dry-run kinds `pj-dry`, `pj-dry-ext` and the control `pj-dry-beatalways` (the freshness line must fail with `stale history served as fresh`) run the stand-in. On a cut whose probe predates `fields=full`, pass `--harness-drift REASON` and set `MK_PROBE_MANIFEST` to a probe built from this tree.

Scenarios (`projection_drills.py`): `projector-me-restart-follow`, `projection-byte-equal-replay`, `history-freshness`. Each runs on the projector binary (pj0 and pj1 both `history_projector` or its control build) or as a dry run on the stand-in (both `projector_stub`); any other plan is refused before a container starts (non-zero exit). On the stand-in, lines it cannot meet are marked `awaits`, recorded with their text, and do not decide a dry run; on the binary every line is judged, except the money tables of B and C (one money projector in the fixture: A's dump is recorded). A line that needs another line's precondition names it in `consequence_of` and is judged only when that line holds. A control kind passes only when at least one judged line fails with the kind's control text and no other judged line fails or is inconclusive. In the follow drill the successor text is judged from fault (b) on, and only for a projection that applied nothing after a fault once the member it followed started a new order-journal recording (read from that member's archive catalog); any other projection behind the head is `projection behind the core head` (a source left before (b) shows so on (a)). Between (d) and (e), (d2) stops the writing copy with SIGSTOP: the standby takes over, and the replay the hung copy recorded must be gone `ORPHAN_STOP_BOUND_MS` after the takeover (judged on the external driver; on the embedded one a stopped copy keeps no subscription and the line records `exercised: false`); the hung copy is then killed and restarted. After (d) and (f) no core member serves more money-projector replays than the baseline's total over the members (the members together no more), each member at most the history replays the running projection slots report open on it in their /health, and the members' `/dev/shm` together at most the baseline total plus `SHM_BASELINE_SLACK_BYTES`; at the end every projector and core container is running and every restart found the drill's own kill or stop. The byte-equal drill reads B and C from members other than A's (`sources.json` names the three; when A and B do not leave exactly one member for C, that line is inconclusive), requires the dumps equal on their fixed columns as well, and points gw0 at C's database while C rebuilds: gw0 starts first on the empty database, pj1 commits `C_BATCH_EVENTS` (default 1) per batch, and reads count once the schema exists (D: every read before C's first beat is 503, and gw0's `gateway_history_reads_total` across that span counts the heartbeat cause and no other). Every step writes `drill/sources.json`.

`history-freshness` sets the gateway slots' `GATEWAY_HISTORY_STALE_MS` and `GATEWAY_HISTORY_PROBE_MS` (`HISTORY_STALE_MS` 3000, `HISTORY_GATEWAY_PROBE_MS` 2000, recorded). (b) freezes pj0 for `FREEZE_S` (8), past the gateway's stale bound plus its probe cadence and below the projector's driver bound (`PROJECTOR_DRIVER_BOUND_MS`): gw0's /health must read stale while pj0 is frozen, and after SIGCONT pj0 must still run `THAW_EXIT_WAIT_S` later. A second freeze of `FREEZE_LONG_S` (12) lies past the driver bound: pj0 resumes or exits 70 on its driver rule (its F3b line, or the Aeron client's service-interval line with the interval above its timeout), an exit is started again as a supervisor would, and history must read fresh again; any other exit fails. (d) cuts the attached member by dropping on the receiving side (INPUT at both ends). (e) measures the leaderless window from the killed leader's container `FinishedAt` to the first row where a survivor leads, with the watcher started `WATCH_LEAD_S` before the kill. (g) slows the member pj0 reads from. On the binary, the drill first finds pj0's replay port (a counting rule on each bound UDP port for `REPLAY_PORT_PROBE_S`, the port with the most packets from the member) and then lets one packet in `SLOW_KEEP_EVERY` (default 40) of the member's UDP to that port through, dropping the rest on pj0's side; pj0's archive control and cluster sessions are untouched. It records pj0's counters over `SLOW_S` with no rule and again with the rule on; the slowdown shows as a rise of its BEHIND count or as its lag in events above the baseline's largest in `SLOW_LAG_SAMPLES` (default 2) consecutive samples. The step then needs a switch away inside the window, with the BEHIND count risen between the last baseline sample and the switch, and a beat after it; no switch fails, and a switch without that rise left a silent member, not a slow one, and is inconclusive (the projector's own leave lines are recorded). On the stand-in the rule drops `SLOW_DROP_PERCENT` (default 80) at random, and the step holds only when the rule dropped packets and pj0's mean probe time per poll (`polls`, `probe_ms_total`, `probe_unanswered`) reached `SLOW_WITNESS_PERCENT` (default 150) of that baseline, or a probe went unanswered. A beat is a change of the database's `beat_at`, whatever wrote it. Steady history ages are judged against `HISTORY_FRESH_AGE_BOUND_MS` alone.

Tools: `projection_dump.py` (canonical COPY dump plus SHA256SUMS; no wall-clock column is dumped, and a column a table has beyond its fixed list is dumped after them and recorded as `extra_columns`, with a second hash of the fixed columns alone, `sha256_fixed`) and `replay_count.py` (run inside a core member: open replays = sender-position counters on the replay streams, plus `/dev/shm` bytes). Every bound is a setting in `projection_drills.SETTINGS`, overridden by an environment variable of the same name.

## Nightly

`nightly.py --plan nightly-cut.json --evidence-root DIR --harness-commit SHA --tools-repo DIR --ct-repo DIR` runs a fixed plan of `{kind, scenario}` entries from a `git archive` of the pinned tools commit (a modified or extra file refuses the night). It takes a heavy-job lock without waiting (a held lock or foreign load ends the night `SKIPPED_BUSY`, exit 75), records stale earlier nights as `INTERRUPTED`, enforces `NIGHTLY_BOUND_S` (default 5 h) and writes `SHA256SUMS` last. Nothing is pushed or published.

Paths are settings, never machine defaults. A night reads them from the environment, and an entry whose path is unset ends `INCONCLUSIVE` with a message naming the variable:

| Variable | Used by | What it points at |
|---|---|---|
| `NIGHTLY_LOCK`, `NIGHTLY_CUT`, `NIGHTLY_CT_REPO` | `nightly.py` | heavy-job lock file, release cut manifest, cluster-tools checkout (falls back to `CUT_CT_REPO`) |
| `CUT_TOOLS_REPO`, `CUT_CT_REPO`, `CUT_OLD_PINS` | `release_cut.py` | tools and cluster-tools checkouts, previous pin set |
| `MK_RUNS`, `MK_BIN_A`, `MK_BUILD_B`, `MK_NC_DIR`, `MK_CUT_NC_DIR`, `MK_DRIVER_PROPERTIES`, `MK_AE_JAR`, `MK_ME_JAR`, `MK_PROJECTOR_JAR`, `MK_PROBE_MANIFEST`, `MK_NETFILTER_HELPER`, `MK_GATEWAY_NC`, `MK_GATEWAY_NC_NO_CANCEL_REOFFER_RULE`, `MK_GATEWAY_NC_NO_ASSET_CHECK` | `mk_manifests.py` | run directory, C++ binaries and build trees, negative-control builds, external driver properties, engine and probe artifacts |
| `CORE_PROBE_CORE_JAR` | `test_story.py` | the core jar the story tests compile and run against (unset: they skip) |
| `LEGACY_TEMPLATE`, `LEGACY_JARS` | `legacy_tag.py` | v0.5.0-beta manifest template and jars |
| `XVER_LEGACY_RUNS`, `XVER_SEEDS`, `XVER_CUT` | `xver.py` | cross-version run inputs |

Each module's docstring lists the exact meaning of its variables.

Two plan sets on alternating nights: `nightly.py --alternate nightly-cut-embedded.json nightly-cut-external.json ...` runs the embedded set on an even UTC day of the year and the external set on an odd one, so both driver modes run every 48 h while each night stays under the bound. The sets are balanced by measured walls: the embedded set is the default plan followed by five replica drills with the engines and replica embedded (peer loss loud, supplier loss, replica restart, replica wipe, re-bootstrap); the external set is the nine replica drills on the external kinds, the other four embedded replica drills (member kill -9, peer loss, the shadow catalog and leader loss) and the five controls (one mode each), then the three history projection drills on the projector binary in both modes (`pj-ext`, `pj`; about 32 min measured for the six). Every drill runs in both modes every 48 h. `NIGHTLY_PLAN_SET=embedded|external` forces a set (a measured run of one set). The chosen set, the parity and whether it was forced are in the night's `summary.json` (`plan_set`). Both files must be the plans at the pinned commit.

Tools has no CI workflow: run the unit tests (`python3 -m unittest discover -s runtime-e2e -p 'test_*.py'`) locally before pinning a harness commit for the nightly.

It runs from a local systemd user timer, not CI. `systemd/` holds the service, the timeout drop-in and the timer (daily at 03:17); install steps and the environment to edit are in the comments of `systemd/runtime-e2e-nightly.service`.
